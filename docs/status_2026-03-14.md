# Status Snapshot: 2026-03-14

This document captures the current state of the `lubobot` repository after:

- the ORB-SLAM3 wrapper evaluation and fork
- the Humble desktop container workflow work
- the live monocular ORB-SLAM integration path
- the local IMU bridge import and first hardware validation pass

It is intended to answer two questions:

1. what is already present and working
2. what is still pending before the first useful robot PoC

## High-Level State

The repository has moved from a small Create 2 bringup skeleton to a multi-component ROS 2 workspace with:

- `robolubo` as the robot application package
- `imu_bridge` as a local ROS 2 package for the MPU6050 serial bridge
- `external/ros2_orb_slam3` as the maintained ORB-SLAM3 fork dependency
- a Humble desktop development container with GPU and serial passthrough support

The project is not yet at full PoC stage, but the main infrastructure required to get there now exists.

## What Exists Today

### 1. Base robot bringup

`robolubo` still provides the original Create 2 bringup path:

- base launch
- Create 2 driver config
- RViz launch
- keyboard teleop launch

That part remains the entry point for the wheel-odometry side of the robot.

### 2. Local `imu_bridge` package

The ROS-side portion of the MPU6050 project has been vendored into:

- [`src/imu_bridge`](/home/alexis/lubobot/src/imu_bridge)

What this package currently does:

- opens the STM32 USB CDC serial device
- reads the existing 16-byte packet format
- publishes `/imu/data_raw`
- starts `imu_filter_madgwick` via launch to produce `/imu/data`

What was intentionally left out from the original external repo:

- STM32 firmware
- toy URDF visualization
- package-local RViz demo config

That split was deliberate. The firmware remains external. The ROS bridge is now part of the robot repo.

### 3. ORB-SLAM3 fork integration

The ROS 2 ORB-SLAM3 dependency now lives in:

- [`external/ros2_orb_slam3`](/home/alexis/lubobot/external/ros2_orb_slam3)

The fork has already been patched to:

- remove workspace-hardcoded runtime paths
- work across the Humble/Kilted header differences that mattered
- build bundled third-party libraries from source
- support a minimal live monocular mode
- publish a pose topic

The robot-facing launch surface for this is kept in `robolubo`, not in the fork.

### 4. Live monocular ORB-SLAM launch path

`robolubo` now has:

- [`src/robolubo/launch/orbslam_mono.launch.py`](/home/alexis/lubobot/src/robolubo/launch/orbslam_mono.launch.py)

This launch path:

- assumes a camera topic already exists
- starts the ORB-SLAM3 monocular node in live mode
- optionally launches RViz

It does not yet launch a camera driver itself.

### 5. Humble development container

The repository now includes a Humble desktop container workflow that supports:

- x86_64 desktop validation against a Humble userspace
- GPU-specific compose overrides for AMD and NVIDIA hosts
- host UID/GID-matched user mapping
- passwordless `sudo` in the dev image
- `vim` installed in the dev image
- automatic sourcing of:
  - `/opt/ros/humble/setup.bash`
  - `/workspaces/ros2_ws/install/setup.bash`
- manifest-based rosdep dependency caching at image-build time
- serial passthrough via an optional compose override

Operator commands now are:

- `just ros-up`
- `just ros-shell`
- `just ros-attach`
- `just ros-build`
- `just ros-down`

### 6. Serial passthrough support

The container workflow now supports serial devices robustly enough for the current IMU use case.

Important behavior:

- serial passthrough is not part of the base compose file
- it is enabled through a serial-specific override file
- helper scripts auto-detect local serial hardware and include that override

The serial override exposes:

- `/dev`
- `/run/udev`

and applies device cgroup rules for:

- `ttyACM*` (major 166)
- `ttyUSB*` (major 188)

This was necessary because bind-mounting `/dev` alone was not enough; Docker still blocked opening the serial device with `EPERM`.

## What Is Partially Done

### IMU runtime validation

The IMU launch now starts:

- `imu_bridge_node`
- `imu_filter_madgwick`

What is not yet fully recorded/validated:

- actual `/imu/data_raw` publish rate
- actual `/imu/data` output content
- physical axis sanity check
- stationary noise characteristics
- whether frame conventions match the eventual robot mounting

The infrastructure and serial access are in place, but the sensor-output validation is still pending.

### Camera and vSLAM

The ORB-SLAM live path exists, but the camera side is still incomplete.

What is missing:

- camera driver bringup in `robolubo`
- webcam mode inspection workflow
- actual camera calibration files
- ORB-SLAM config derived from the real webcam intrinsics
- final TF integration for camera mounting

So vSLAM is structurally prepared but not yet usable on the real hardware stack.

## Pending Work

### 1. Finish IMU validation

This is the next immediate step.

Need to confirm:

- `/imu/data_raw` exists and is stable
- `/imu/data` exists and contains filtered orientation
- the sensor axes behave sensibly under simple physical motions

Concrete checks:

- `ros2 topic hz /imu/data_raw`
- `ros2 topic echo /imu/data_raw --once`
- `ros2 topic echo /imu/data --once`
- manual tilt / rotation tests

### 2. Decide IMU frame convention

Before fusion, the project needs a clear answer for:

- what `imu_link` means
- how the board will be mounted on the robot
- whether a static transform will be required between `base_link` and `imu_link`

This is not optional. Frame mistakes here will contaminate later odom fusion.

### 3. Add `robot_localization`

Once IMU output is trusted, the next architectural step is:

- fuse wheel odometry from Create 2
- fuse IMU orientation/angular velocity
- produce a cleaner local odom estimate

This should happen before serious camera SLAM integration.

### 4. Add camera bringup

The next hardware-facing task after IMU validation is:

- add a camera driver launch path in `robolubo`
- most likely `usb_cam`

This should expose:

- device path
- frame id
- resolution
- frame rate
- image topic naming

### 5. Calibrate the webcam

This must happen before real monocular ORB-SLAM use.

Important distinction:

- intrinsics can be calibrated off-robot on the dev PC
- extrinsics depend on the robot mount and come later

What is needed:

- checkerboard-based intrinsic calibration
- saved camera YAML
- ORB-SLAM monocular config generated from the real camera model

### 6. Validate live ORB-SLAM with the real camera

After camera bringup and calibration:

- run the live ORB-SLAM launch
- confirm tracking starts
- confirm pose topic updates
- inspect drift and relocalization behavior

The current EuRoC config is only a placeholder and should not be treated as a valid robot camera calibration.

### 7. Integrate localization stack

The first meaningful robot-state pipeline should become:

- wheel odom from Create 2
- IMU raw + filtered orientation
- EKF/localization fusion
- then camera SLAM on top

This ordering is important. The robot should have a reasonable local odom estimate even if camera tracking drops.

## Known Rough Edges

### `ros-down` warning

`just ros-down` can warn:

```text
Warning: No resource found to remove for project "docker"
```

when no shared compose project is active.

That warning is harmless, but the project naming/path behavior in the current compose invocation could be cleaned up later.

### Upstream ORB-SLAM3 compiler warnings

`ros2_orb_slam3` still emits upstream warnings from bundled third-party code and ORB-SLAM internals.

Those warnings are noisy, but they are not currently blocking builds.

### IMU covariance tuning

The imported IMU bridge uses placeholder covariance values.

Those should be treated as temporary until real sensor behavior is measured.

## Recommended Next Order

If work continues from this state, the pragmatic next sequence is:

1. finish IMU runtime validation
2. define IMU frame semantics and mounting assumptions
3. add `robot_localization` with wheel odom + IMU
4. add camera driver bringup
5. calibrate webcam intrinsics
6. replace placeholder ORB-SLAM settings with real camera settings
7. validate live ORB-SLAM
8. then decide whether the monocular setup is sufficient for the intended PoC

## Bottom Line

The repo now has the core scaffolding required for the PoC:

- reproducible Humble desktop environment
- external ORB-SLAM fork integrated into the workspace
- local IMU bridge package integrated into the workspace
- serial passthrough working in Docker
- live ORB-SLAM launch surface in `robolubo`

What is still missing is no longer foundational repo plumbing.

The remaining work is now mostly hardware validation and state-estimation integration:
